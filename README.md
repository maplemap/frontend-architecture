# 🏛️ Frontend Architecture Patterns

Це спроба зібрати популярні (або не дуже) архітектурні підходи для фронтенд‑розробки.  
Кожна папка містить приклад або шаблон певної архітектурної моделі, яку можна використовувати або адаптувати для проєктів різної складності.

## 🔧 Мета

- Порівняння підходів (структура, відповідальність, масштабованість)
- Демонстрація практичної реалізації кожного підходу
- Формування власної архітектурної стратегії для масштабних застосунків

## 📁 Список архітектурних підходів

- [`atomic-design`](./atomic-design) — Компонентний підхід до UI, поділений на атоми, молекули, організми
- [`classic-layered`](./classic-layered) — Класична трирівнева структура: UI / логіка / доступ до даних
- [`clean-architecture`](./clean-architecture) — Адаптація Clean Architecture для фронтенду з інверсією залежностей
- [`ddd`](./ddd) — Domain-Driven Design: поділ за bounded contexts і агрегаціями
- [`event-driven`](./event-driven) — Подієва архітектура на основі шини подій (event bus)
- [`fsd`](./fsd) — Feature-Sliced Design — функціонально-модульний підхід
- [`micro-frontends`](./micro-frontends) — Мікрофронтенди з незалежним життєвим циклом модулів
- [`modular`](./modular) — Простий модульний поділ коду без строгих шарів
- [`monorepo`](./monorepo) — Організація проєкту як monorepo з розділеними пакетами
- [`reactive`](./reactive) — Реактивна архітектура з фокусом на потоки подій та реакцію на зміни стану

## ✅ Про архітектуру

Архітектура — це набір модулів (будівельних блоків), компонентів системи, опис того, як ці модулі повинні розроблятися, 
а також опис зв’язків між цими модулями. Крім того, архітектура включає створення інтерфейсів, які визначають, 
для чого призначений кожен модуль.

### Що не є архітектурою
Архітектура — це не вибір технологій, це вибір та формування меж, усередині яких правильне рішення стає очевидним для всієї команди.
Коли контекст, обмеження та цілі визначені правильно — оптимальне рішення не потрібно “вигадувати”, воно **випливає природно** в рамках встановлених меж.

### Питання, на які має відповідати архітектура
- **Хто буде підтримувати систему?**  
  (команда, компетенції, онбординг, ротація)

- **Які в нас терміни та ресурси?**  
  (швидкість доставки, доступні люди, критичні дедлайни)

- **Які існують жорсткі або негнучкі обмеження?**  
  (регуляторні вимоги: PCI DSS, HIPAA, SOC2, стандарти безпеки)

- **Як ми вимірюємо успіх архітектури?**  
  (швидкість розробки, масштабованість, стабільність, продуктивність, кількість інцидентів)

- **[Опціонально] Який рівень ризику ми готові прийняти?**  
  (експерименти, нові технології, складні залежності, інфраструктурні рішення)

### Якою повинна бути хороша архітектура
- Передбачувана
- Придатна до повторного використання
- Зручна у супроводі
- Масштабована
