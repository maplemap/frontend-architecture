# Modular Architecture

## Що це
**Modular Architecture — це архітектурний підхід, у якому фронтенд ділиться на незалежні модулі (modules), 
кожен із яких повністю інкапсулює свою частину функціоналу.**  
Модуль — це «міні-застосунок» зі своїми компонентами, логікою, сторінками, сервісами та публічним API.  
Модулі не втручаються один в одного й взаємодіють лише через чітко визначені інтерфейси.

## Головна Ідея
> **Модуль — це ізольований бізнес-домен із власною структурою та одним публічним входом (`index.ts`).**

## Ментальна Мапа

### 📦 Модулі (Modules)
Кожен модуль містить:

- UI-компоненти
- бізнес-логіку
- локальний стейт
- API-запити
- утиліти
- сторінки (якщо належать модулю)

Приклади модулів:

- `auth`
- `catalog`
- `cart`
- `profile`
- `checkout`
- `dashboard`

Кожен модуль — автономна одиниця організації коду.

### 🔄 Залежності
У Modular Architecture **немає вертикальних шарів**, як у FSD.  
Натомість головне правило таке:

> **Модулі можуть залежати один від одного лише через публічний API.**

Це означає:

- ✔ `cart` → `auth/index.ts` — дозволено
- ✖ `cart` → `auth/internal/logic.ts` — заборонено

Таким чином модуль лишається ізольованим і передбачуваним.

## Переваги
- Чіткі кордони: модуль — повністю самостійний блок
- Зрозумілі точки інтеграції між модулями
- Можна переносити або виносити модулі в окремі пакети
- Команди можуть працювати в паралелі над різними модулями
- Добре підходить для середніх і великих проєктів
- Зручно тестувати модулі в ізоляції

## Недоліки
- Потрібно слідкувати за залежностями, інакше виникає хаос
- Без правил може з'явитися «мікромоноліт» у межах одного модуля
- Не всі модулі ростуть рівномірно
- Потребує дисципліни: публічні інтерфейси, документація, структура

## Коли Обирати
- Проєкт складається з чітких бізнес-зон
- Команда розбита на підгрупи (auth team, catalog team тощо)
- Потрібно масштабувати роботу незалежних команд
- Проєкт середнього або великого розміру

## Як Впроваджувати
- Визначити ключові домени → створити модулі (`auth`, `catalog`, `cart`, `profile`)
- Усередині кожного модуля створити власну структуру (`ui`, `model`, `api`, `lib`)
- Забезпечити єдиний публічний вихід з модуля через `index.ts`
- Заборонити імпорти з внутрішніх директорій інших модулів
- Налаштувати ESLint-правила для контролю залежностей
- Розвивати модулі незалежно, не створюючи крос-модульний хаос
