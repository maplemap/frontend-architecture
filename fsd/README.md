# Feature-Sliced Design (FSD)

## Що це
**FSD — це архітектурний підхід, який організовує фронтенд у вигляді незалежних бізнес-блоків (features), розташованих 
по чітких шарах (layers).**  
Кожна функція живе у своїй «коробці», а залежності дозволені лише зверху вниз.

## Головна Ідея
> **Спочатку визначаємо бізнес-домен (slice) → потім шар (layer) → потім пишемо код.**

## Ментальна Мапа

### ↕ Шари (Layers)
Рівні абстракції від фундаменту до UI:

- **shared** — утиліти, ui-kit, базові сервіси
- **entities** — бізнес-сутності: User, Product, Order
- **features** — завершені користувацькі дії
- **pages** — маршрути, що збирають фічі
- ~~**processes** — довгі сценарії (checkout, onboarding)~~ (deprecated)
- **app** — ініціалізація застосунку, router, providers

**Правило:** імпорти тільки вниз по ієрархії.

Чим нижче шар — тим він "глухіший".
Він не знає нічого про те, що вище.

### ↔ Зрізи (Slices)
Горизонтальне розбиття за бізнес-доменами:

- `auth`
- `catalog`
- `cart`
- `profile`
- інші бізнес-області

Кожен зріз містить свої entities → features → pages.  
Зрізи не змішуються між собою.

## Переваги
- Чітка, передбачувана структура
- Менше конфліктів: кожен працює у своїй фічі
- Контроль залежностей через ESLint та alias’и
- Легка еволюція: зміни не ламають інші частини

## Недоліки
- Потрібен час на онбординг
- Зайва деталізація для дрібних застосунків
- Потребує alias’ів, lint-правил і генераторів
- Міграція займає час

## Коли Обирати
- Продукт довгоживучий та активно росте
- Команда 3+ розробників
- Є складні бізнес-сутності та сценарії

## Як Впроваджувати
- Починати з user story: визначити slice → зібрати entities → створити features → додати pages
- Тримати публічний API через `index.ts`
- Новий код — одразу за FSD, старий переносити поступово
