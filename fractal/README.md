# Fractal Architecture

## Що це
**Фрактальна архітектура — це підхід, у якому кожна частина системи має таку саму внутрішню структуру, як і вся система.**  
Компонент, фіча, модуль або домен виглядають однаково структурно — просто на різному масштабі.  
Це дає передбачуваність, ізоляцію та легке масштабування.

## Головна Ідея
> **Ті самі принципи, структура і правила повторюються на всіх рівнях —  
> компонент = фіча = модуль = домен = застосунок (у мініатюрі).**


## Ментальна Мапа

### 🔁 Фрактальні Рівні (Fractal Levels)

На будь-якому рівні системи структура виглядає подібно:

- **ui/** — компоненти інтерфейсу
- **model/** — логіка, state, реактивність
- **api/** — робота із зовнішніми джерелами
- **lib/** — утиліти, хелпери
- **index.ts** — публічний API (зовнішня точка входу)

Один і той самий шаблон може застосовуватися до:

- маленького компонента (`Button/`)
- фічі (`AddToCart/`)
- цілого домену (`Cart/`)
- навіть до всього застосунку (`src/`)

**Фрактальність = однакові правила на різних масштабах.**



### 🔄 Залежності
У фрактальній архітектурі головне правило:

> **Кожен елемент має власний публічний API і не повинен лізти у внутрішні файли інших елементів.**

Тобто:
- ✔ `cart/index.ts` → `auth/index.ts` — дозволено
- ✖ `cart/model/logic.ts` → `auth/ui/LoginForm.tsx` — заборонено

Фіча поводиться як незалежний міні-проєкт.



## Переваги
- Передбачувана структура на всіх рівнях
- Легко масштабувати продукт
- Легко онбордити розробників (правило одне для всіх рівнів)
- Компоненти, фічі та модулі автономні
- Можна переносити частини системи без хаосу
- Природна сумісність з FSD, Modular, DDD та Microfrontends
- Проста інтеграція з подійною (event-driven) логікою



## Недоліки
- Потрібна дисципліна (кожен елемент мусить мати API)
- Можна перевантажити систему «надмірною однаковістю»
- Відсутність чітких глобальних шарів може ускладнити великі команди
- Потрібно контролювати залежності лінтерами або правилами каталогу



## Коли Обирати
- У проєктів зі складною інтерфейсною логікою
- У real-time застосунків (мапи, телеметрія, dashboards)
- У систем, які ростуть непрогнозовано та довго
- Коли в команді багато паралельних потоків розробки
- Коли структура має бути однакова на рівні «кнопки» і на рівні «домену»



## Як Впроваджувати
- Використовувати однакову структуру (`ui/`, `model/`, `api/`, `lib/`) у всіх елементах
- Кожен блок оформлювати як «міні-проєкт» із власним `index.ts`
- Забезпечити ізоляцію через публічні API
- Розрізати великі частини системи на підфрактали, які легко розвивати окремо
- Застосовувати фрактальність зверху вниз та знизу вверх (компонент ↔ домен)
- Поєднувати фрактальний підхід із FSD або Modular для глобальної структури
